# Migrating to v0.24.1 — the `blur` / `perf` prop regroup

v0.24.1 does two things: it **regroups the anti-blur and performance props**
into two dedicated `<Camera>` prop objects (`blur` and `perf`), and it
**flips two stitch defaults** based on on-device A/B measurement.

This applies whether you're on **0.23.x or 0.24.0** — both shipped the older,
scattered prop shape (`frameSelection.antiBlur`, perf levers inside `stitcher`).

> [!IMPORTANT]
> The prop regroup is a **breaking** compile-time change — the fields **moved**,
> they were not renamed, so the migration is a mechanical find/replace. There is
> no runtime shim. (It lands as a PATCH, 0.24.1, only because 0.24.0 was already
> published; on the 0.x line — API-unstable by design, see `CHANGELOG.md` — this
> would normally be a minor bump.)

---

## 1. Anti-blur → the `blur` prop group

Every motion-blur defense now lives in **one** `blur` object. Previously it
was split between `frameSelection.sharpnessWindow` and
`frameSelection.antiBlur.*`.

```tsx
// ❌ v0.23
<Camera
  frameSelection={{
    maxKeyframes: 8,
    sharpnessWindow: 4,
    antiBlur: {
      maxExposureMs: 8,
      maxCommitPanRateRadPerSec: 1.0,
      minScoreFractionOfMedian: 0.6,
      preferHighFpsFormat: true,
    },
  }}
/>

// ✅ v0.24 — the gate stays in frameSelection; blur moves to `blur`
<Camera
  frameSelection={{ maxKeyframes: 8 }}
  blur={{
    sharpnessWindow: 4,
    maxExposureMs: 8,
    maxCommitPanRateRadPerSec: 1.0,
    minScoreFractionOfMedian: 0.6,
    preferHighFpsFormat: true,
  }}
/>
```

| v0.23 location | v0.24 location |
| --- | --- |
| `frameSelection.sharpnessWindow` | `blur.sharpnessWindow` |
| `frameSelection.antiBlur.maxExposureMs` | `blur.maxExposureMs` |
| `frameSelection.antiBlur.maxCommitPanRateRadPerSec` | `blur.maxCommitPanRateRadPerSec` |
| `frameSelection.antiBlur.minScoreFractionOfMedian` | `blur.minScoreFractionOfMedian` |
| `frameSelection.antiBlur.maxConsecutiveHolds` | `blur.maxConsecutiveHolds` |
| `frameSelection.antiBlur.preferHighFpsFormat` | `blur.preferHighFpsFormat` |

`blur` is deep-merged over the SDK defaults (all defenses ON), so you can set
one knob without restating the rest. To **disable** a mechanism set it to `0` /
`false` (or `sharpnessWindow: 1`). See the [`blur` reference](../camera-api.md).

## 2. Perf levers → the `perf` prop group

The stitch-**speed** levers moved out of `stitcher` (which now carries only the
stitch *recipe*) into a dedicated `perf` object.

```tsx
// ❌ v0.23 — perf levers mixed into the stitcher recipe
<Camera
  stitcher={{
    warperType: 'spherical',
    blenderType: 'multiband',
    seamFinderType: 'voronoi',
    rangeMatcherWidth: 3,
    numThreads: 0,
    adaptiveStitchMode: 'measured',
  }}
/>

// ✅ v0.24 — recipe in `stitcher`, speed levers in `perf`
<Camera
  stitcher={{ warperType: 'spherical', blenderType: 'multiband' }}
  perf={{
    seamFinderType: 'voronoi',
    rangeMatcherWidth: 3,
    numThreads: 0,
    adaptiveStitchMode: 'measured',
  }}
/>
```

| v0.23 location | v0.24 location |
| --- | --- |
| `stitcher.seamFinderType` | `perf.seamFinderType` |
| `stitcher.rangeMatcherWidth` | `perf.rangeMatcherWidth` |
| `stitcher.numThreads` | `perf.numThreads` |
| `stitcher.adaptiveStitchMode` | `perf.adaptiveStitchMode` |
| `stitcher.adaptiveMinOutputMP` | `perf.adaptiveMinOutputMP` |
| `stitcher.adaptiveSlowStitchMsPerFrame` | `perf.adaptiveSlowStitchMsPerFrame` |
| `defaultSeamFinder` prop (flat) | `perf.seamFinderType` |

`stitcher` still carries `stitchMode` / `warperType` / `blenderType` /
`enableMaxInscribedRectCrop` / `debugPack`. Setting a perf lever on `stitcher`
is now a **type error**.

## 3. Two default flips

If you never set these, your captures change as follows. Both are backed by an
on-device A/B (A35 + iPhone, 5 and 8–10 keyframes, same frames re-stitched).

### `seamFinderType`: `graphcut` → **`voronoi`**

The seam finder is the single dominant stitch-speed lever. Voronoi is **1.6–1.9×
faster** and was **visually identical** to graphcut across both devices and
frame counts (no ghosting or seam tears; SSIM ~0.95 where output dims match). If
your corpus has strong near-field parallax (where seam *placement* matters), you
can keep graphcut:

```tsx
<Camera perf={{ seamFinderType: 'graphcut' }} />
```

### `numThreads`: `1` (single) → **`0`** (auto multi-core)

Single-threading was chosen for peak-RAM safety, but the 8–10 keyframe ablation
measured it **consistently slower** than multi-core (−12…−23% on the A35); it
also matches iOS, which is always multi-core. Multi-core uses more peak RAM — if
a device regresses on memory, the single-thread kill-switch is still there:

```tsx
<Camera perf={{ numThreads: 1 }} />
```

`numThreads` is Android-only (iOS's GCD backend ignores it).

## Quick reference

| What | v0.23 | v0.24 |
| --- | --- | --- |
| Anti-blur knobs | `frameSelection.{sharpnessWindow, antiBlur.*}` | **`blur`** |
| Speed levers | `stitcher.{seamFinderType, rangeMatcherWidth, numThreads, adaptive*}` | **`perf`** |
| Seam default | `graphcut` | **`voronoi`** |
| Threads default | `1` (single) | **`0`** (multi) |
| `stitcher` prop | recipe **+** speed levers | recipe only |
| `frameSelection` prop | gate **+** anti-blur | gate only |

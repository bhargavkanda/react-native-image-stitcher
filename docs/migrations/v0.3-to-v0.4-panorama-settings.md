# Migrating from `PanoramaSettings` v0.3 → v0.4

> _Historical — this v0.3 → v0.4 guide references slit-scan / hybrid panorama
> settings that were removed in v0.15.0 (see the CHANGELOG)._

`react-native-image-stitcher` v0.4 splits the flat 45-field
`PanoramaSettings` interface from v0.3 into three engine-discriminated
hierarchical types.  Hosts that constructed `PanoramaSettings` literals
or imported `DEFAULT_PANORAMA_SETTINGS` get a TypeScript compile error
on first install.  This guide walks through the migration path.

> [!IMPORTANT]
> **No automated migration helper or compatibility alias is shipped.**
> v0.4 deletes the v0.3 type by design — the audit (in `CHANGELOG.md`'s
> v0.3.0 entry) proved most v0.3 fields were dead surface on the
> `<Camera>` batch-keyframe path.  A compile-time error is the safer
> failure mode than a silent runtime mismatch.

---

## What changed at a glance

```
                    v0.3 (flat)                           v0.4 (hierarchical)

                ┌──────────────────────┐             ┌──────────────────────────┐
                │ PanoramaSettings     │             │ PanoramaSettings         │
                │  • captureSource     │             │  ├ captureSource         │
                │  • debug             │             │  ├ debug                 │
                │  • stitchMode        │             │  ├ stitcher              │
                │  • warperType        │             │  │   ├ stitchMode        │
                │  • blenderType       │   ───▶      │  │   ├ warperType        │
                │  • seamFinderType    │             │  │   ├ blenderType       │
                │  • flowMaxCorners    │             │  │   ├ seamFinderType    │
                │  • flowMaxTranslat…  │             │  │   └ enableMaxInscr…   │
                │  • frameSelectionMo… │             │  └ frameSelection        │
                │  • incrementalEngine │             │      ├ mode              │
                │  • slitWidthFraction │             │      ├ maxKeyframes      │
                │  • paintMode         │             │      ├ overlapThreshold  │
                │  • planeSource       │             │      └ flow (optional)   │
                │  • nccSearchRadius1d │             │          ├ maxCorners    │
                │  • … 30+ more fields │             │          ├ maxTranslat…  │
                │                      │             │          └ … 4 more      │
                │  (mixed three        │             │                          │
                │   engines' fields)   │             │ + SlitscanSettings      │
                │                      │             │ + HybridSettings        │
                └──────────────────────┘             └──────────────────────────┘
```

The three new top-level types are **engine-discriminated**:

- `PanoramaSettings` — what `<Camera>` consumes (always batch-keyframe).
- `SlitscanSettings` — for hosts that drive `incremental.start({ engine: 'slitscan-*', ... })` directly.
- `HybridSettings` — for the RetaiLens-specific hybrid live engine.

Each type carries only the fields its target engine actually reads.
The 2026-05-22 audit (CHANGELOG v0.3.0) traced every field to its
native consumer; fields with no consumer in the host's chosen engine
were removed from that engine's type.

## Migration recipes

Pick the recipe that matches how your host code uses `<Camera>` /
`PanoramaSettings` today.

### Recipe 1 — You import `DEFAULT_PANORAMA_SETTINGS` and pass it as-is

**Before (v0.3):**
```ts
import { Camera, DEFAULT_PANORAMA_SETTINGS } from 'react-native-image-stitcher';

<Camera
  // … no settings prop used; <Camera> uses its internal default
/>
```

**After (v0.4):** Zero changes needed.  `<Camera>` still builds the
correct initial settings internally via its `default*` props.

---

### Recipe 2 — You construct a `PanoramaSettings` literal

**Before (v0.3):**
```ts
import type { PanoramaSettings } from 'react-native-image-stitcher';

const mySettings: PanoramaSettings = {
  captureSource: 'ar',
  debug: false,
  stitchMode: 'auto',
  warperType: 'plane',
  blenderType: 'multiband',
  seamFinderType: 'graphcut',
  enableMaxInscribedRectCrop: false,
  frameSelectionMode: 'flow-based',
  keyframeMaxCount: 6,
  keyframeOverlapThreshold: 0.20,
  flowNoveltyPercentile: 0.85,
  flowEvalEveryNFrames: 5,
  flowMaxTranslationCm: 50,
  flowMaxCorners: 150,
  flowQualityLevel: 0.01,
  flowMinDistance: 10,
  // … plus 25+ v0.3 fields you probably set to defaults
};
```

**After (v0.4):**
```ts
import type { PanoramaSettings } from 'react-native-image-stitcher';

const mySettings: PanoramaSettings = {
  captureSource: 'ar',
  debug: false,
  stitcher: {
    stitchMode: 'auto',
    warperType: 'plane',
    blenderType: 'multiband',
    seamFinderType: 'graphcut',
    enableMaxInscribedRectCrop: false,
  },
  frameSelection: {
    mode: 'flow-based',
    maxKeyframes: 6,
    overlapThreshold: 0.20,
    flow: {
      noveltyPercentile: 0.85,
      evalEveryNFrames: 5,
      maxTranslationCm: 50,
      maxCorners: 150,
      qualityLevel: 0.01,
      minDistance: 10,
    },
  },
};
```

Or, equivalently, spread the new default and override only what you
care about:

```ts
import {
  type PanoramaSettings,
  DEFAULT_PANORAMA_SETTINGS,
} from 'react-native-image-stitcher';

const mySettings: PanoramaSettings = {
  ...DEFAULT_PANORAMA_SETTINGS,
  captureSource: 'non-ar',
  stitcher: {
    ...DEFAULT_PANORAMA_SETTINGS.stitcher,
    stitchMode: 'scans',
  },
};
```

> [!TIP]
> **The `frameSelection.flow` sub-tree is optional in the type but
> non-optional in practice.**  The bridge always emits the flow
> defaults to native — but for clarity, prefer setting `flow`
> explicitly (even just to `DEFAULT_PANORAMA_SETTINGS.frameSelection.flow`)
> in custom literals.  Or use the new `DEFAULT_FLOW_GATE_SETTINGS`
> standalone export.

### Recipe 3 — You used v0.3 fields that no longer exist

The v0.3 fields below were either slit-scan-specific (the `<Camera>`
batch-keyframe path never read them) OR had no native consumer at all.
They're **gone from `PanoramaSettings`** in v0.4.  Their new home (if
any) is on the per-engine type that actually reads them.

| v0.3 field | v0.4 location | Notes |
|---|---|---|
| `incrementalEngine` | (deleted) | `<Camera>` always uses `'batch-keyframe'`; the choice was inert in the modal.  Hosts that need slit-scan or hybrid construct `SlitscanSettings` / `HybridSettings` and call `incremental.start({ engine: ..., config: ... })` directly. |
| `useARPreview` | superseded by `captureSource` | `'ar'` / `'non-ar'` is the canonical axis. |
| `useDetectedPlane` | `SlitscanSettings.plane.source` | Set to `'ARKitDetected'` or `'Disabled'`. |
| `planeSource` | `SlitscanSettings.plane.source` | Same field, different home. |
| `virtualPlaneDepthMeters` | `SlitscanSettings.plane.virtualDepthMeters` | |
| `arkitPlaneAlignmentThreshold` | `SlitscanSettings.plane.alignmentThreshold` | |
| `planeProjectionStyle` | `SlitscanSettings.plane.projectionStyle` | |
| `slitWidthFraction` | `SlitscanSettings.advanced.panAxisFractionRect` | Renamed to match the native `kPanAxisFractionRect` config key. |
| `sliverPosition` | `SlitscanSettings.painting.sliverPosition` | |
| `firstFrameFullFrame` | `SlitscanSettings.painting.firstFrameFullFrame` | |
| `paintMode` | `SlitscanSettings.painting.paintMode` | |
| `acceptGate` | (deleted) | Legacy v13 knob; no engine reads it anymore.  If you need slit-scan accept gating, use `SlitscanSettings.advanced.minAcceptDeltaPx`. |
| `enableTriangulation` | `SlitscanSettings.registration.enableTriangulation` | |
| `enableTriAccumulator` | `SlitscanSettings.registration.enableTriAccumulator` | |
| `enable2dNcc` | (collapsed) | Set the `SlitscanSettings.registration.ncc2d` sub-object to enable; leave undefined to disable. |
| `enableRansacHomography` | `SlitscanSettings.registration.enableRansacHomography` | |
| `nccSearchRadius1d` | `SlitscanSettings.registration.ncc1d.searchRadius` | Presence-as-enable: set `ncc1d` sub-object to enable. |
| `nccSearchMargin2d` | `SlitscanSettings.registration.ncc2d.searchMargin` | |
| `nccConfidenceThreshold2d` | `SlitscanSettings.registration.ncc2d.confidenceThreshold` | |
| `enableNcc2dEmaSmoothing` | (collapsed) | Set `ncc2d.emaSmoothing` to enable. |
| `ncc2dEmaAlpha` | `SlitscanSettings.registration.ncc2d.emaSmoothing.alpha` | |
| `enableNcc2dPanAxisLock` | (collapsed) | Set `ncc2d.panAxisLock` to enable. |
| `ncc2dCrossAxisLockPx` | `SlitscanSettings.registration.ncc2d.panAxisLock.crossAxisLockPx` | |
| `hybridProjection` | `HybridSettings.projection` | |
| `maxRecordingMs` | (deleted) | Legacy video-recording fallback; never reached `<Camera>`'s engine path. |
| `framesPerSecond` | (deleted) | Same. |
| `minFrames` / `maxFrames` | (deleted) | Same. |
| `quality` | (deleted) | The lib's JPEG-quality knobs are now per-call (e.g., `incremental.start({ snapshotJpegQuality })`). |

> [!NOTE]
> **"Presence-as-enable" pattern.**  Several v0.3 boolean fields
> (`enable1dNcc`, `enable2dNcc`, `enableNcc2dEmaSmoothing`,
> `enableNcc2dPanAxisLock`) collapse into a single optional sub-object
> in v0.4.  The sub-object's PRESENCE means "enabled":
>
> ```ts
> // v0.3
> { enable2dNcc: true, nccSearchMargin2d: 14, nccConfidenceThreshold2d: 0.95 }
>
> // v0.4
> {
>   ncc2d: {
>     searchMargin: 14,
>     confidenceThreshold: 0.95,
>   },
> }
> ```
>
> The JS→native bridge expands this back to the boolean wire format
> automatically.  See `panoramaSettingsToNativeConfig` (and its
> sibling adapters) in `src/camera/PanoramaSettingsBridge.ts` for the
> exact mapping.

### Recipe 4 — You drive slit-scan or hybrid engines directly

If your host code calls `incremental.start({ engine: 'slitscan-rotate', ... })`
or similar (bypassing `<Camera>`), you were already constructing a
config dict by hand.  v0.4 gives you typed shapes for both engines:

```ts
import {
  DEFAULT_SLITSCAN_SETTINGS,
  slitscanSettingsToNativeConfig,
  type SlitscanSettings,
} from 'react-native-image-stitcher';
import { incremental } from 'react-native-image-stitcher';

const slitscanSettings: SlitscanSettings = {
  ...DEFAULT_SLITSCAN_SETTINGS,
  variant: 'slitscan-rotate',
  registration: {
    ...DEFAULT_SLITSCAN_SETTINGS.registration,
    ncc1d: { searchRadius: 20 },  // Presence-as-enable.
    ncc2d: {
      searchMargin: 12,
      confidenceThreshold: 0.99,
      // emaSmoothing + panAxisLock omitted → disabled.
    },
  },
};

await incremental.start({
  engine: slitscanSettings.variant,
  config: slitscanSettingsToNativeConfig(slitscanSettings),
  // … other start options
});
```

Same shape for `HybridSettings` + `hybridSettingsToNativeConfig`.

The bridge adapters are the single source of truth for the JS→native
wire format.  Always use them — don't construct the flat config dict
by hand.

## Verification checklist

After migrating:

- [ ] `tsc --noEmit` (or your project's typecheck) is clean.  v0.4
      types should catch every renamed/deleted field at compile time.
- [ ] Search your codebase for any remaining `PanoramaSettings`
      property name from the deleted list (Recipe 3 table) — string
      literals or comments referencing the old names may linger.
- [ ] If you previously parsed/persisted user settings (e.g.,
      via AsyncStorage), migrate stored shapes before passing to
      `<Camera>`.  See "Storage migration" below.

## Storage migration

If you persist settings (e.g., via AsyncStorage) and a user has
v0.3-shape settings on-device, you need a one-time read-side migration:

```ts
import {
  DEFAULT_PANORAMA_SETTINGS,
  type PanoramaSettings,
} from 'react-native-image-stitcher';

type LegacyV03Settings = {
  // Only fields the host actually persisted; usually a subset
  captureSource?: 'ar' | 'non-ar';
  stitchMode?: 'auto' | 'panorama' | 'scans';
  blenderType?: 'multiband' | 'feather';
  flowMaxTranslationCm?: number;
  // … etc
};

function migrateV03ToV04(legacy: LegacyV03Settings): PanoramaSettings {
  return {
    ...DEFAULT_PANORAMA_SETTINGS,
    captureSource: legacy.captureSource ?? DEFAULT_PANORAMA_SETTINGS.captureSource,
    stitcher: {
      ...DEFAULT_PANORAMA_SETTINGS.stitcher,
      stitchMode: legacy.stitchMode ?? DEFAULT_PANORAMA_SETTINGS.stitcher.stitchMode,
      blenderType: legacy.blenderType ?? DEFAULT_PANORAMA_SETTINGS.stitcher.blenderType,
    },
    frameSelection: {
      ...DEFAULT_PANORAMA_SETTINGS.frameSelection,
      flow: {
        ...DEFAULT_PANORAMA_SETTINGS.frameSelection.flow!,
        maxTranslationCm: legacy.flowMaxTranslationCm
          ?? DEFAULT_PANORAMA_SETTINGS.frameSelection.flow!.maxTranslationCm,
      },
    },
  };
}
```

(Or, after migrating once, persist the new shape and drop the
migration helper.)

## Why the breaking change?

The flat v0.3 type made it look like every `<Camera>`-consuming host
needed to think about all 45 fields.  In reality:

- `<Camera>` always runs the `batch-keyframe` engine internally
- That engine reads ~16 of the 45 v0.3 fields
- The other ~29 were either slit-scan-specific, hybrid-specific, or
  had no native consumer at all

The flat type was a maintenance hazard: changes to slit-scan settings
would TypeScript-impact every `<Camera>` host even though `<Camera>`
never read them.  The v0.4 split eliminates that coupling at the type
level — `<Camera>`'s `PanoramaSettings` only contains fields its
engine actually consumes.

It also enables a clearer story for Layer 2 hosts: hosts driving
slit-scan or hybrid engines directly now have a typed contract
that names exactly the knobs their chosen engine reads — no more
"which of these 45 fields will my engine actually look at?"
guessing.

See `CHANGELOG.md`'s `[Unreleased]` v0.4 section for the full
field-mapping table.

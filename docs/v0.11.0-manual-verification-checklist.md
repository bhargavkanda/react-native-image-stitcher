## Test 1 — non-AR mode panorama still produces stitched output

> Equivalent to plan Phase 1 Task 3 + Phase 4 Task 8 Step 1.

This is the **single most important** test.  The whole point of
v0.11.0 is that we refactored `useFrameProcessorDriver` into a thin
wrapper around `useStitcherWorklet`, and the example app now wires
`<Camera frameProcessor={exampleFrameProcessor}>` (composed) instead
of letting `<Camera>` use its built-in driver internally.  If the
refactor missed a shared value, or `stitcher.call` doesn't actually
get invoked, panorama capture in non-AR mode silently produces
no stitched output.

### Steps

1. Install + launch the example app on the device.
   - iOS: `npx react-native run-ios --udid 00008140-001E092208A2201C
     --no-packager`
   - Android: `./example/android/gradlew -p example/android :app:installDebug`
     then launch from the home screen.
2. Switch capture source to **non-AR** (the toggle in the top
   chrome — opposite of "AR" if it defaults to AR).  The
   `<Camera>` should re-mount on vc's path.
3. Tap **panorama mode** and start a capture; pan across a
   well-textured indoor scene (bookshelf, painting, anything with
   features).  Aim for ~3-5 accepted keyframes.
4. Stop the capture.  The PanoramaConfirmModal appears with the
   stitched output.

### PASS criteria

- The stitched output **is visibly present** (not blank, not a
  single frame).
- The accepted-frame count visible in the modal is **non-zero**
  and roughly matches what you panned through.
- Metro logs show `[example] useFrameProcessor tick — source=vc`
  lines firing at roughly the frame rate (you'll see the cumulative
  count ticking up).  This confirms the **composed** worklet body
  is running — both the host tick log AND first-party stitching.

### FAIL signals + likely causes

| Signal | Likely cause |
|---|---|
| Modal opens with blank output / 0 accepted frames | `stitcher.call(frame)` isn't running.  Check `exampleFrameProcessor` is correctly bound in `App.tsx`; check `stitcher.isReady` resolves on mount. |
| Modal opens with output that looks wrong (stretched / blurred) | A shared value moved during refactor.  Compare the `useStitcherWorklet.ts` worklet body against the pre-refactor `useFrameProcessorDriver.ts` (`git show v0.10.0:src/stitching/useFrameProcessorDriver.ts`). |
| Metro logs show **NO** `[example] useFrameProcessor tick` lines in non-AR mode | The host worklet didn't bind.  Check `<Camera frameProcessor={...}>` prop is set + non-null. |
| Logs show **only** tick lines, no panorama output | The `stitcher.call` inside the worklet is short-circuiting on plugin == null.  Wait a couple seconds after camera mount before tapping panorama. |

## Test 2 — AR mode unchanged

> Equivalent to plan Phase 4 Task 8 Step 2.

The v0.11.0 refactor is pure TS in non-AR scope.  AR mode dispatch
goes through `__stitcherProxy` (Phase 4b.i / 4b.iii) and doesn't
touch this code path.  But verify nothing accidentally regressed.

### Steps

1. Switch capture source to **AR**.
2. Capture a panorama same way as Test 1.

### PASS criteria

- Stitched output visibly present (same standard as Test 1).
- Metro logs show `[example] useFrameProcessor tick — source=ar`
  lines.  These prove the AR-side dispatch is fanning out to the
  host worklet (auto-registered via `__stitcherProxy`).

### FAIL signals

If AR mode regresses, it's likely a bundling / dependency issue
(the new `useStitcherWorklet` adds nothing AR mode reaches).
`git revert` the v0.11.0 commits and re-bisect.

## Test 3 — v0.10.0 PR B refine pill still works

> Verifies the v0.10.0 fix didn't bit-rot under the v0.11.0
> refactor.  The bug we hand-fixed in `IncrementalStitcherBridge.swift`
> (RCTEventEmitter.sendEvent → bridge.enqueueJSCall) is verified by
> JS contract test in `src/stitching/__tests__/subscribeIncrementalState.refine.test.ts`
> — but the bridge layer itself can only be exercised on-device.

### Steps

1. Complete a panorama capture (non-AR or AR — either works).
2. In the confirm modal, tap **Re-refine**.

### PASS criteria

- Blue progress pill appears with stage labels:
  `validating → stitching → writing → done`.
- Pill auto-dismisses ~3s after `done`.
- Metro logs show `[example] state event` lines with non-undefined
  `refineStage` values, one per stage.

### FAIL signals

| Signal | Implication |
|---|---|
| No pill appears | The iOS bridge fix may have regressed.  Check `git show v0.10.0:ios/Sources/RNImageStitcher/IncrementalStitcherBridge.swift` vs current. |
| Pill appears but never advances past `validating` | `refinePanorama` may be erroring early.  Check Console.app for fileLog entries in `[refine.progress]`. |

## Test 4 — Composition demo round-trip (the v0.11.0 deliverable)

> Equivalent to plan Phase 2 Task 5.

This is the new behaviour v0.11.0 ships.  We're confirming the
composition pattern works: host worklet (the example tick log) AND
first-party stitching fire simultaneously from one composed
`useFrameProcessor` body.

### Steps

1. Non-AR mode panorama capture (as Test 1).
2. Watch Metro logs in real time during the capture.

### PASS criteria

- Throughout the capture: Metro shows BOTH:
  - `[example] useFrameProcessor tick — source=vc cumulative: ar=0 vc=<N>`
    (`<N>` ticking up at ~1 Hz per the throttle in `App.tsx`)
  - `[example] keyframe accepted at ...` (first-party stitching
    firing per accepted frame)
- The stitched output is sane (per Test 1's PASS criterion).
- No double-counted events; no stale plugin warnings.

### FAIL signals

| Signal | Implication |
|---|---|
| Only the host tick log fires; no `keyframe accepted` lines | `stitcher.call(frame)` is short-circuiting.  Check `stitcher.isReady` flow. |
| Only first-party stitching fires; no tick log | `fireFrameProcessorLog` isn't running.  Check the host worklet body order in `App.tsx` (`stitcher.call(frame); fireFrameProcessorLog(...);`). |
| Both fire but acceptance count is much lower than v0.10.x baseline | The refactor introduced a throttle that didn't exist before.  Check `sharedEvalEveryN` is being read correctly inside `useStitcherWorklet`. |

## What to do when all 5 tests pass

Move to Phase 5 (Release) — bump version to `0.11.0` in
`package.json`, add the changelog entry under `[Unreleased]`, commit
`chore(release): v0.11.0`, tag, push.

Or — since Phase 5 has been done autonomously as part of this
session (see commit history on `feature/v0.11.0-non-ar-composition`),
just merge the PR after verification.

## What to do when a test fails

- Tests 1, 4, 5 (composition / non-AR core): blocker.  Don't merge
  until root-caused.  The most likely culprits are listed in each
  test's FAIL signals.  Per the v0.11.0 plan blocker policy: "do
  not paper over with thresholds."
- Test 2 (AR mode regression): blocker.  Should be impossible if
  the diff really is TS-only, but check anyway.
- Test 3 (refine pill): blocker for v0.11.0 only if it regresses
  *here* vs working in v0.10.0; if v0.10.0 was already broken
  somehow, that's a separate v0.10.x fix.
